# ADR-0054 — The toolchain is locked with PEP 751, the runtime lock is Phase 021's, and the lock's verdict is recomputed

## Status

Accepted — Phase 020.

**Date:** 2026-08-16

## Context

`ROADMAP.md` assigns Phase 020 *Dependency Resolution and Lockfile Strategy*, and
eleven places in this repository defer the lockfile to it by name — including
[`../DEPENDENCY_POLICY.md`](../DEPENDENCY_POLICY.md), which states that "nothing
here writes a lockfile and nothing should until the phase that owns the decision
makes it", and `MEMORY.md`, which records that the exact version pins in
`.github/workflows/` are "a reproducibility measure, not a lockfile; Phase 020 owns
the real one".

What exists today is three *declaration* registers — `pyproject.toml`, the
workflows, and `.pre-commit-config.yaml` — which
`tools/quality/supply/inventory.py` reads and compares against each other. Its own
docstring is emphatic that this is "declared, not resolved": it runs no resolver and
claims no transitive tree. Seven development tools are declared with lower bounds;
they resolve to **forty-eight distributions**, of which the workflows pin seven.
Forty-one packages therefore enter this project's environment at whatever version an
index served on the day somebody built it, and nothing records which.

Two further consequences follow from that, and both are worse than the first.
`tools/quality/supply/audit.py` synthesises a requirements file from the inventory
and lets `pip-audit` resolve it against a live index at audit time — so today's
vulnerability report describes a resolution **nobody has ever installed**, and one
that can differ between two runs on the same commit. And
`tools/quality/runtime/gate.py` builds `.venv` from those same seven pins, so a
fresh clone's environment is reproducible in name only.

The evidence for what a lock can and cannot record is in
[`../research/phase_020_sources.md`](../research/phase_020_sources.md). Four of the
load-bearing facts are documented nowhere and were read from installed source: pip's
lock writer sets only `lock-version`, `created-by` and `packages` (S-03); it writes
without controlling line endings (S-04); `pip-audit --locked` reads names and
versions without resolving, and **refuses a lock with no packages** (S-06); and
locking through a PEP 735 dependency group produces byte-identical output to locking
from a requirements file (S-07). pip labels both `pip lock` and `pip install -r
pylock.toml` EXPERIMENTAL (S-02, S-05).

## Decision

**1. The lock format is PEP 751, and the producer is pip.** The file is
`pylock.dev.toml`, at the repository root, generated by `pip lock`, normalised to LF
and committed. The name is not a choice — PEP 751 requires `pylock.toml` or
`pylock.<name>.toml`, and `pip-audit --locked` globs exactly that pattern at a
project path.

**2. The toolchain is locked. The runtime is not, and the pairing is enforced
rather than remembered.** `project.dependencies` is empty and
`tests/contract/test_packaging_contract.py` keeps it so; a lock of an empty set
carries no evidence, duplicates a contract test by being empty, and — decisively —
makes `pip-audit --locked` raise rather than audit (S-06). So no `pylock.toml` is
created here. `docs/engineering/lock-policy.toml` records `[runtime] locked = false`
with its reason, and the gate fails with `LOCK_RUNTIME_UNLOCKED` if
`project.dependencies` ever becomes non-empty while no runtime lock exists. Phase
021 cannot introduce a runtime dependency without producing the lock that goes with
it.

**3. Every claim the lock makes is recomputed from the lock's own evidence.** The
gate does not ask pip whether the lock is good. It parses the lock with `tomllib`,
independently of the vendored reader that wrote it, and recomputes: that every
artefact carries a hash in a permitted algorithm; that every artefact is served over
HTTPS from the declared host, with no credential in the URL and no bare filesystem
path; that at least one recorded wheel filename's PEP 425 tags serve the interpreter
[`../engineering/runtime-contract.toml`](../engineering/runtime-contract.toml) pins;
that each filename's own name and version agree with the entry carrying it; and that
the lock, the three declaration registers and the declared roots agree about one
version each. This follows
[ADR-0052](0052-wheel-availability-is-a-recorded-survey-whose-verdict-is-recomputed.md)
exactly: evidence is recorded so a verdict can be checked rather than believed.

**4. What the lock cannot say is declared beside it.** Because a pip-produced lock
records no interpreter requirement, no index, no markers and no producer version
(S-03), `docs/engineering/lock-policy.toml` is hand-written and records the target,
the index, the artefact host, the producer and its version, the permitted hash
algorithms, and the roots the lock was resolved from. Nothing generates that file.
A declaration a tool rewrites is a mirror, which is the position
`wheel-survey.toml`, `mutation-baseline.toml` and `action-pins.toml` already take.

**5. The lock is load-bearing: it is installed from, and it is what is audited.**
`scripts/bootstrap.ps1` builds `.venv` from `pylock.dev.toml`, and
`python -m tools.quality supply` audits it with `pip-audit --locked`. An absent or
unreadable lock during bootstrap is a **refusal**, never a silent fall back to the
pins — a fallback is used on precisely the day the lock is wrong. `--from-pins`
restores the previous behaviour as a deliberate act, for the reason Decision 7
gives.

**6. The exact version pins in `.github/workflows/` survive, and become derived
rather than authoritative.** A pip-produced lock is valid for one interpreter and
one platform (S-02), so it cannot serve the 3.12 entry in the CI matrix, and the
`mutation` and `shards` jobs deliberately install subsets. The gate makes a pin that
disagrees with the lock a failure and names the exact replacement, so the two cannot
drift apart. The lock is **not** added to `inventory.drift()`: that module states
about itself that it reads manifests and runs no resolver, and a lock is resolved.

**7. This rests on two surfaces pip labels EXPERIMENTAL, and that is stated rather
than absorbed.** Recomputing the verdict (Decision 3) and keeping `--from-pins`
(Decision 5) are both hedges against exactly that, and they are the reason this
decision is affordable now rather than after the label is removed.

**This decision does not cover** which packages are declared, the first runtime
dependency, adopting PEP 735 dependency groups, or widening the SBOM from the
declared set to the locked transitive set. The first two are Phase 021's; the third
is recorded as considered and deferred in
[`../engineering/DEPENDENCY_LOCKING.md`](../engineering/DEPENDENCY_LOCKING.md) on the
evidence in S-07; the fourth is a genuine improvement and a genuinely separate
change.

## Consequences

**Forty-eight distributions are pinned by hash where seven were pinned by version.**
That is the gain, and it is the whole point.

**A fourth file must be kept in step, and the gate is what keeps it.** Upgrading a
tool is now a five-step procedure — relock, read the gate's named pin edits, apply
them to the workflows and the pre-commit revisions, update the declaration's date,
rebuild the environment — where it used to be editing one string.
`DEPENDENCY_LOCKING.md` writes it out, and every partial commit is red.

**Bootstrap is slower and installs more.** A fresh `.venv` takes forty-eight wheels
rather than seven, and the CI `runtime` job's timeout rises from ten minutes to
fifteen. That figure is a judgement from the change in wheel count, not a
measurement on a runner, and it is commented as such.

**A behaviour Phase 017 delivered has changed.** `_install_toolchain` no longer
installs the workflow pins by default. This is the second time a Phase 017
deliverable has been altered by a later phase, and the justification is narrow: a
gate comparing the environment against the lock cannot exist if the environment is
built from something else, because it would be red on a clean tree the day it was
written.

**The audit's scope roughly doubles, and its meaning changes more than its size.**
`pip-audit` now reports on the set that is actually installed rather than on a
resolution performed at audit time. `DEPENDENCY_POLICY.md`'s claim that the audit,
the SBOM and the manifest "all describe one set" becomes true of the installed set;
the SBOM still renders from the declared inventory, and that residual inconsistency
is recorded rather than left silent.

**Enforcement is a gate, a command-table entry and seven test modules**, not a
convention. `python -m tools.quality lock` reaches nothing and runs offline;
`lock installed` compares this environment; `relock` and `upgrade` reach the index
and are therefore subcommands, following the split `runtime bootstrap` and
`wheels probe` already make.

**One thing the gate cannot check, and says so.** pip records no dependency edges,
so nothing offline can prove that every locked package is reachable from a declared
root. Roots are compared in both directions; an orphaned *transitive* package is
closed by relocking, not by inspection. Naming this is what stops the gate reading
as more thorough than it is.

## Alternatives Considered

**Adopt `uv`, `poetry` or `pdm` as the resolver and lock producer.** Each produces a
better lock than pip does — real dependency edges, multi-platform resolution, and a
single-package upgrade as a first-class operation rather than a constraints-file
trick. Rejected on two counts, and the licence and cost were not among them. It
would be a new tool in the toolchain, which needs the written review
[ADR-0044](0044-dependency-review-is-a-written-process-with-a-generated-inventory.md)
requires — affordable, but it would land in the phase whose job is the lock rather
than the declaration. More importantly it moves resolution to a tool whose output
this repository would have to trust, at the moment it is trying to stop trusting
output; pip is already present, already the thing that installs, and is what
`pip-audit` reads. Worth revisiting if PEP 751 support in pip stops moving, or if
the missing dependency edges become the binding constraint.

**Generate a hash-pinned requirements file from `pip install --report`, and verify
it with repository-native code.** The most self-reliant option, and closest to
[ADR-0033](0033-mutation-testing-is-a-repository-native-ast-harness.md)'s precedent.
Rejected because it invents a private format where a standard exists, and it would
forgo `pip install -r pylock.toml` and `pip-audit --locked` — both of which arrive
free and are what make the lock load-bearing rather than decorative. Writing a lock
nothing installs from would have produced a file that agrees with the environment
only by coincidence.

**Lock the runtime as well, for symmetry.** Rejected on evidence rather than taste:
`pip-audit --locked` raises `PyLockSourceError` on a lock with no packages (S-06),
so committing an empty `pylock.toml` would break the vulnerability gate this phase
strengthens. The forward hook in Decision 2 is what stops the asymmetry being
forgotten.

**Trust `pip lock`'s output and check only that the file parses.** Cheapest, and it
is what most projects do. Rejected because pip labels the feature EXPERIMENTAL, and
because a lock is exactly the kind of file that is read by machines and never by
people — a hand edit, a truncated write or a shape change between pip releases would
all pass a parse check. It is also the option this repository has already refused
twice, in ADR-0052 and
[ADR-0053](0053-drift-is-measured-against-an-accepted-baseline-and-repair-is-a-classification.md).

**Keep the CI pins as the only mechanism and defer locking again.** Rejected because
it is the position the repository already holds, and eleven documents describe it as
temporary. It covers seven distributions of forty-nine and leaves the audit
describing a resolution nobody installed.

**Adopt PEP 735 dependency groups in the same change.** Rejected on measurement: pip
accepts `--group` on `pip lock`, but its lock constructor never sets the
corresponding fields and the unset ones are dropped, so the artefact is
byte-identical (S-07). It would touch a contract-tested invariant and three test
modules for no observable difference in what this phase delivers.

## Risks and Trade-offs

**The characteristic failure is an experimental surface moving underneath this.**
pip could change what `pip lock` emits, or the `install -r pylock.toml` path could
regress, and either would land in the one command somebody runs before they have a
working tree. The observable signal is `LOCK_VERSION_UNSUPPORTED` or
`LOCK_PACKAGE_MALFORMED` firing on a lock nobody edited, or `bootstrap.ps1` failing
on a fresh clone. The mitigations are deliberate: the gate refuses rather than
guesses when it meets a shape it does not implement, `--from-pins` restores the
previous behaviour without a code change, and `[producer]` records the pip version
the lock was made with so a moved version is visible rather than inferred.

**The second risk is that the recomputation is itself wrong.** This gate contains a
second, independent reader of PEP 751, and a bug in it would either reject a good
lock — noisy, and quickly found — or accept a bad one, which is silent. The
asymmetry is why the property tests assert the direction that matters: a lock with
any hash removed never passes, at every position, and a package whose every wheel
tag is for another platform is never compatible.

**A smaller but real trade-off: the lock is single-platform, and the repository is
single-platform.** Anyone bootstrapping on anything but Windows on the pinned
interpreter cannot install from this lock. That is already true of
`runtime-contract.toml` and of the Windows-only CI matrix, which `MEMORY.md` records
as settled; the lock inherits the constraint rather than adding one. If the project
ever supports a second platform, this record needs a second lock rather than an
amendment.

**Confidence is high on the shape and moderate on the durability.** The four
source-level facts were read from the installed build and are certain for pip
26.1.1; they are not promises about pip 27. That is precisely what
`[producer] version` exists to make visible.
