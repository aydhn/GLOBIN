# ADR-0044 — Dependency review is a written process over a generated inventory, and the SBOM is generated here

## Status

Accepted — Phase 014.

## Context

[ADR-0003](0003-zero-budget-open-source-dependency-policy.md) promised that
"Phase 014 defines that process", and eleven places in the repository have been
waiting for it. `pytest-xdist` ([ADR-0036](0036-test-execution-is-sharded-by-a-stable-digest-not-by-a-plugin.md)),
`mutmut` ([ADR-0033](0033-mutation-testing-is-a-repository-native-ast-harness.md))
and a YAML parser ([ADR-0043](0043-ci-trust-is-declared-in-a-manifest-and-every-job-is-bounded.md))
were each refused with the same sentence: Phase 014's review process "does not
exist yet".

Meanwhile the repository had three registers describing one toolchain and nothing
comparing them. `pyproject.toml`'s `dev` extra carries lower bounds. The workflow
installs exact versions. `.pre-commit-config.yaml` pins a hook revision, and its
own comment states that the revision must match the version the gate runs "so the
hook and the gate cannot disagree about whether a file is clean".

**A correction to an earlier draft of this record.** That draft said nothing
checked it. That was wrong: `test_the_hook_ruff_and_the_ci_ruff_are_the_same_version`
in `test_quality_contract.py` has compared the ruff pair since Phase 004, and it
is the check that actually caught the first Dependabot pull request this phase
produced. What was missing is narrower than "nothing": that check names `ruff`
in two hand-written regular expressions, so it covers one pair and would not
notice a second hook added later. The inventory generalises it to any
`<tool>-pre-commit` repository against any pinned distribution.

## Decision

**1. The inventory is generated; the review is written.** `tools/quality/supply/inventory.py`
reads the three registers and reports where they disagree. `docs/engineering/dependency-reviews.toml`
records a human's verdict on each declared dependency — licence, where that
licence was read, review date, reason. A contract test compares them in both
directions.

The split matters. A generated file that also carried the reasoning would be
regenerated over the reasoning. A hand-written file that also listed the
dependencies would drift from what is declared. Each file holds the half nothing
else can supply, which is the same shape `action-pins.toml` already uses.

**2. Reviewing is six questions, answered in writing.** Transitive cost, licence
and its source, maintenance, runtime versus development, could-this-be-written,
and what-breaks-if-it-disappears. `docs/DEPENDENCY_POLICY.md` is the process.

**3. `pip-audit` is adopted through that process, as its first subject.** It is
also the most expensive thing in the toolchain: six declared packages resolved to
almost nothing, and adding it takes the audited set to twenty-six distributions.
That cost is recorded rather than glossed. It is development-only, runs in one CI
job, and is not in `full`.

**4. The audit runs against a requirements file generated from the inventory,
not against the ambient environment.** The first implementation audited whatever
was installed, which on a developer's machine meant their whole user-level
site-packages — `--strict` correctly refused a local package that is on no index,
and the gate failed for a reason having nothing to do with GLOBIN. Transitive
coverage is not lost: `pip-audit` resolves the file before auditing it.

**5. The SBOM is generated by this repository rather than by a tool.**
CycloneDX 1.7, from the same inventory. `cyclonedx-py` would produce a richer
document and would stamp each run with a random `serialNumber` and the wall
clock, so two runs over one unchanged tree would produce two files with two
digests. A digest that changes when nothing changed is not evidence. Pinning
those fields down would mean overwriting the fields the tool supplied.

The serial is a UUID version 5 over the commit; the timestamp is the commit's own
committer date. The gate builds the document **twice** and compares the
renderings byte for byte, because asserting determinism proves nothing and
comparing it costs almost nothing.

**6. Dependabot opens pull requests and decides nothing.** No auto-merge. ADR-0043
refused a bot because "a bot that opens the pull request does not perform the
review"; the review now exists, so the bot is useful. Its version-comment format
is deliberately the one this repository's pin policy requires, so a Dependabot
pull request is compliant when it opens rather than in violation of it.

**7. CodeQL uses advanced setup.** Default setup is configured in a control plane
no commit can review, diff or explain. Everything else this repository trusts is
version controlled. It was verified `not-configured` before the workflow was
added, so nothing was overridden.

## Consequences

- The `dev` extra grows from six to seven, and the contract test that pinned it
  at six is rewritten to assert the rule the number stood in for: nothing may be
  declared without a review record. That is strictly stronger — a count permits
  swapping one tool for another silently and forbids a reviewed adoption.
- `github/codeql-action` is the first non-`actions/*` program this repository
  executes. Admitted through a named allowlist with a stated reason, and a test
  requires the reason to be long enough to be an argument.
- The workflow parser moved from the contract test into `tools/quality/supply/workflows.py`,
  because `tools` cannot import `tests` and a second copy would drift. The test
  now imports it and still exercises every function against deliberately broken
  input.
- Pin checks now read **every** workflow rather than `quality.yml` by name. The
  second workflow this phase adds would otherwise have been unchecked.
- The deferral register can be revisited. `pytest-xdist`, `mutmut` and a YAML
  parser now have a process to be reviewed under; this ADR does not review them,
  and none is adopted here.

## Alternatives Considered

**Query OSV directly from repository-native code**, in the manner of ADR-0033's
mutation harness. Refused, and it was close. Advisory matching is version-range
arithmetic across several ecosystems' conventions, and getting it subtly wrong
produces a gate that reports "no vulnerabilities" while missing them — precisely
the failure this phase exists to prevent. Writing that by hand would trade a
dependency for a correctness risk in the one place correctness matters most. The
SBOM generator was written by hand because *serialisation* is the kind of thing
hand-written code gets exactly right; range-matching is not.

**Use `cyclonedx-py` and post-process its output.** Rejected: at that point the
tool supplies fields which are then overwritten, and the determinism still
depends on knowing every volatile field it might add in a future version.

**Keep the count of six and refuse `pip-audit`.** Rejected. The count was a proxy
for "no unreviewed dependency", and Phase 014 exists to make reviewed adoption
possible. Refusing the phase's own required tool to preserve a proxy for the rule
the phase implements would be the proxy outranking the rule.

**Audit the installed environment.** Rejected after it failed in practice — see
decision 4.

## Risks and Trade-offs

**The audited set is now much larger than the declared one.** Twenty-six
distributions rather than seven, and `pip-audit` is why. If one of *its*
dependencies has an advisory, this repository's gate fails for a reason that has
nothing to do with GLOBIN's own code. That is the honest cost of having an audit
at all, and the waiver mechanism exists partly for it.

**The severity threshold is blunt.** Any open finding fails, at any severity.
Affordable while the toolchain is seven development-only packages; it will need to
become severity-aware when Phase 021 introduces runtime dependencies.

**The hand-written SBOM validator is not a schema validator.** It checks what
this generator could plausibly get wrong. A conforming document that this
generator cannot produce would pass unremarked. Stated rather than hidden: the
alternative is `jsonschema` plus a vendored schema nobody rechecks.

**`_satisfies` understands only `>=`.** Every specifier in this repository is
`>=`, and anything else is accepted rather than guessed at. A gate that cried
wolf on a specifier it misread would be a gate somebody switches off. Full
PEP 440 comparison is `packaging`, and that is Phase 020's decision.
